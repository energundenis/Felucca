## 2. Baseline arithmetic findings

Inspection of `test_metal_biquad_process_q30` in this artifact shows:
- native signed 32-bit x 32-bit multiply instructions producing 64-bit results;
- five signed 64-bit divide instructions by the Q30 scale constant in the sample path (one for each coefficient multiply);
- explicit saturation comparisons and branches for output and both DF2T state updates;
- no floating-point instructions in the sample implementation.

The five divide instructions are generated by the original C implementation of round-to-nearest using signed division by (2^{30}). Although the divisor is constant, this target code generation did not reduce those operations to shifts in the inspected object. This is a concrete optimization target, not a runtime cycle measurement.

The block probe's per-sample call is also visible. The production compiler may inline differently under different translation-unit / optimization conditions; this object alone does not establish the final engine render cost.

## 3. Follow-up candidate change

A subsequent test-only candidate commit `f1ef7e80de1c16c072dae267dc4a471c165e7b7b` replaces the signed division with symmetric rounded shifts:
- nonnegative product: `(product + half) >> 30`;
- negative product: `-(((-product) + half) >> 30)`.

The negative branch shifts only a positive magnitude, avoiding implementation-defined right shift of a negative signed value. For int32 × int32, product magnitude is at most (2^{62}), so negation and the rounding bias remain within int64_t.

A new deterministic equivalence regression was added in commit `25b287b3ceb42735f953d0b86e5b83be93ada432`, comparing the shift implementation with the original division oracle across edge pairs and 20,000 deterministic vectors.

**This optimized change has not yet received a fresh GitHub Actions run or a new AC79 artifact.** Do not mark the optimization as verified until both strict host regression and target code-generation inspection pass on the exact updated head.
